# block_curriculummap

医学教育のカリキュラムマップ(DP・コアカリ・マイルストーン × 科目カテゴリのクロス集計)を可視化するMoodleブロックプラグイン。

## 背景・設計意図

科目のディプロマ・ポリシー(DP)、医学教育モデル・コア・カリキュラム(コアカリ)との対応関係を「カリキュラム・マップ」として可視化する。

大学固有のデータ(電子シラバス等)を直接扱うのではなく、Moodle標準のコンピテンシー機能(`core_competency`)をハブにすることで、可視化部分そのものは他大学にも配布可能な汎用資産にする、という設計方針。

```
① 電子シラバス等(大学固有) → ② Moodleコンピテンシー(標準API) → ③ このプラグイン(汎用・配布可能)
```

コンピテンシーのセットアップが済んでいない段階でも使えるよう、CSVアップロードによる代替経路も用意している(下記「データソース」参照)。

## 主な機能

- **3軸+科目カテゴリのクロス集計**: DP・コアカリ・マイルストーンの3軸(それぞれ有効/無効を個別設定可能)と、科目カテゴリ(コースの`idnumber`から自動抽出)を任意に行/列へ配置
- **行列入替・昇順/降順ソート・延べ/ユニーク集計・数値/セグメント表示切替**
- **複数軸フィルタ**(軸間AND・同一軸内OR)
- **比較リスト**(複数科目を選んで他をグレーアウト)
- **サイドバー詳細**: 科目クリックで全軸のタグを表示、Moodleコースへのリンク付き
- **表示モード3種**(ブロックインスタンスごとに設定):
  - `link` (既定): コンパクト表示+別ページへのリンク
  - `modal`: コンパクト表示+ポップアップ(モーダル)で開く
  - `full`: フル可視化をその場に表示
- **データソースを軸ごとに選択可能**:
  - `competency` (既定): Moodleコンピテンシーフレームワークからリアルタイムに読み込み
  - `csv`: 専用アップロード画面からCSVで一括投入(Moodleにコースが存在しない「仮想科目」も表現可能)

## 権限モデル

| capability | 用途 | 既定 |
|---|---|---|
| `block/curriculummap:addinstance` / `:myaddinstance` | ブロックの設置 | 標準的なMoodleのブロック配置権限(editingteacher/manager等)と同様 |
| `block/curriculummap:view` | 閲覧 | **ゲストを含む全員**に許可 |
| `block/curriculummap:manage` | 表示モード変更・フレームワーク紐づけ・CSV取り込みの設定 | **Manager**(管理者は常に可) |

> Moodleのブロック標準`settings.php`はコア側で`moodle/site:config`に固定されているため、**Managerロールはそこに辿り着けない**。そのためこのプラグインでは`settings.php`(サイト管理者向け)とは別に、`manage.php`という独立ページを`block/curriculummap:manage`だけでガードして用意している。ブロック本体のフッターにManagerだけへのリンクを出している。

## インストール

1. このリポジトリを `blocks/curriculummap` として配置
2. Moodleの管理画面(Site administration → Notifications)を開き、アップグレード処理を実行(新規テーブル`block_curriculummap_link`が作成される)
3. ダッシュボードやコース、サイトトップなど任意の場所にブロックを追加
4. Manager権限を持つユーザーでブロックの「フレームワーク紐づけ」リンク(または `blocks/curriculummap/manage.php`)を開き、DP/コアカリ/マイルストーンそれぞれのMoodleコンピテンシーフレームワークidnumber、または利用するデータソース(コンピテンシー/CSV)、科目カテゴリの抽出設定(`course.idnumber`の何文字目から何文字を切り出すか)を設定

## ブロックインスタンスごとの上書き(複数マップの共存)

1つのサイトで「医学部マップ」「看護学部マップ」のように複数のカリキュラムマップを共存させたい場合、ブロックインスタンスごとに設定を上書きできる。

- `manage.php`(instanceidパラメータ無し、またはinstanceid=0) = **サイト共通のデフォルト**。何も上書きしていないブロックは全てこれに従う
- `manage.php?instanceid=<ブロックインスタンスid>` = **そのブロック専用の設定**。ブロック本体のフッターリンクは自動的に自分自身のinstanceidを渡す
- 各軸(dp/core/milestone)は「サイト共通の設定を使う(既定)」「コンピテンシー」「CSV」の3択。「サイト共通の設定を使う」のままなら、サイト全体の設定がそのまま適用される。明示的に切り替えた軸だけが、そのブロック専用の設定になる
- 科目カテゴリの抽出設定(offset/length)も同様に、チェックボックスで「サイト共通を使う/このブロック専用の値を使う」を切り替え可能
- CSVデータも同じ考え方で、`block_curriculummap_link`テーブルの`instanceid`列がNULLなら「サイト共通の共有データ」、実際のブロックインスタンスidが入っていれば「そのブロック専用のデータ」。既存の(このインスタンス概念を導入する前にアップロードした)データは自動的に`instanceid=NULL`のまま=サイト共通として動き続けるので、移行作業は不要

例: 「医学部マップ」ブロックでDPだけ医学部用フレームワークに切り替え、コアカリ・マイルストーンはサイト共通のまま、といった部分的な上書きも可能。

## データソースの詳細

### コンピテンシー経由(既定)

`manage.php`でフレームワークのidnumberを指定すると、`core_competency\api`経由でフレームワークの階層構造(親子関係)と、コース-コンピテンシーの紐づけ(`core_competency\api::list_course_competencies()`)を読み取る。コースへのコンピテンシー紐づけ自体は、Moodle標準の学習プラン管理画面や、別途用意する「コース-コンピテンシー バルクリンクツール」(このリポジトリには含まれない)で行う想定。

### CSV経由

`manage.php`から「CSVデータを取り込む」を開き、以下の形式のCSVをアップロードする(プレビュー→確定の2段階)。

```
course_idnumber, item_idnumber, item_label, parent_label, course_name
2026_M_L3XXXX, I-1, 患者中心の医療, I,
```

- `parent_label`・`course_name`は任意列
- `course_idnumber`が既存のMoodleコースと一致しなくてもエラーにはならない(「仮想科目」として取り込まれ、`course_name`があればそれを、無ければidnumberそのものを表示名にする)。Moodle側にコースがまだ無い段階でもカリキュラムマップの体裁を組み立てられる
- 1科目に複数項目がある場合は複数行に分ける
- アップロードのたびに、その軸の既存データを丸ごと置き換える(最新のみ保持)

## 既知の制限・今後の課題

- **`amd/build/`は現時点で手動同期**: この開発環境では`npx grunt amd`が使えず、`amd/src/curriculummap.js`(素のAMD `define()`形式で記述、ES importは未使用)と`amd/build/curriculummap.js`・`amd/build/curriculummap.min.js`を**内容が同一になるよう手動でコピー**している。本来Moodleの規約では`amd/build/`は生成物なのでリポジトリに含めない/`.gitignore`対象とすべきだが、grunt環境を用意するまでの暫定措置としてコミットしている。grunt環境を整えたら、この3ファイルをビルド成果物に置き換え、`amd/build/`を`.gitignore`する運用に切り替えることを推奨
- **コース-コンピテンシーの紐づけ取得(`get_course_links()`)がサイト内の全コースを走査する実装**: 設計上の想定スケール(1大学あたり100〜300科目程度)では問題ないが、より大規模なサイトでは要見直し(バッチSQL化・キャッシュ等)
- **フレームワーク改訂時のバージョニング運用は未実装**: Moodleのコンピテンシーフレームワークの`archived`状態を使うか、常に最新版のみ見せるかは今後の検討事項
- **マイルストーンはDP/コアカリと並列・独立した軸**として扱っている(DP項目ごとに異なるマイルストーン値を持つケースは現行ルール上発生しないため)。将来そのルールが変わった場合は、マイルストーンをDP小項目配下の階層として持たせる再設計が必要になる
